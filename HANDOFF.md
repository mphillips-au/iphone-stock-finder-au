## Production `/api/status` investigation (unresolved — needs the user's Cloudflare dashboard access)
User reported `https://iphone-stock-finder-au.mphillips-au.workers.dev/api/status` still shows `{"indexed":false,"storeCount":0,...}` ~2 hours after the background-indexer feature (see the "Background nationwide indexer" entry below) was merged to `master` with a real D1 `database_id` already in `wrangler.jsonc` (confirmed via `git status`/`git log` — the committed file has the real id, not the old placeholder).
**Diagnosis so far:** `readStatus()` (`src/lib/telstra/snapshot.ts`) returns this *exact* shape both when `env.DB` is completely unbound (the `/api/status` handler's explicit fallback in `src/worker.ts`) and when a correctly-bound D1 has simply never been written to — so the response alone can't distinguish "DB not bound in production" from "cron has never fired". This sandbox has no outbound access to the Cloudflare API (`npx wrangler whoami` fails with a network error here), so cron-trigger registration and scheduled-invocation logs could not be checked directly — only the plain HTTPS `curl` to the deployed worker's own URL, which is not a Cloudflare API call, works.
**Most likely cause:** Cloudflare's dashboard/Git-integration auto-deploy ("Workers Builds") does not always register `wrangler.jsonc`'s `triggers.crons` the way a direct `wrangler deploy` does — HANDOFF's own "Manual Cloudflare deployment record" and "Background nationwide indexer" entries below note that no actual `wrangler deploy` has been run since the real D1 id was added; only the dashboard Git auto-deploy has. If the Cron Trigger was never registered, `scheduled()` simply never runs, `stores`/`sync_state` stay empty, and `/api/status` reports exactly what's being seen.
**What the user needs to check (cannot be done from this sandbox):** In the Cloudflare dashboard, open this Worker → **Settings → Triggers** (or **Trigger Events**) and confirm a Cron Trigger for `*/15 * * * *` actually exists. If it's missing, either add it manually there, or run an authenticated `npx wrangler deploy` from a machine with real Cloudflare access (this provisions cron triggers the same way `wrangler.jsonc` declares them). Also worth checking the Worker's **Logs**/**Observability** tab for any invocation errors on the `scheduled` handler in case it's firing but throwing (e.g., a D1 binding or migration mismatch) — `src/worker.ts`'s `scheduled()` swallows errors unless `DEBUG_UPSTREAM=true` is set, so a silent failure there wouldn't show up without checking real-time logs.

## Session update — Background nationwide indexer, last-updated badge, store map
User's explicit ask: with public release imminent, prevent hundreds of concurrent visitors from causing Telstra rate limits/blocks by replacing live per-visitor Telstra calls with a background snapshot refreshed every 15 minutes; add a "last updated" badge; add a free map/geolocation feature. Confirmed direction: staggered indexing, and index only this app's own tracked SKUs (never an open-ended SKU list). This is a genuine architecture pivot, not a routine follow-up — AGENTS.md's non-negotiable architecture section was updated alongside the code (see its "Background nationwide indexer" additions) rather than diverging from it silently.

**What changed:**
- New Cloudflare D1 database (binding `DB`, schema in `migrations/0001_init.sql`: `stores`, `stock`, `sync_state` tables).
- New `src/lib/telstra/indexer.ts`: `runIndexCycle(db, ctx)` pages Telstra's store list from a single fixed seed point (Sydney CBD — arbitrary, since distance-ordered pagination is exhaustive from any seed, just affects discovery order not coverage), querying only `TRACKED_SKUS` (new export in `src/data/products.ts`, the existing 40-SKU fallback catalogue). Reuses the existing `stockPage()` batching/413-split/retry logic unchanged. Stops a run when the shared request budget (`ctx.remaining`, same 40-attempt cap live scans use) runs low, persisting a `{from, emptyStreak}` cursor in `sync_state` so the next cron tick resumes — this is the "staggered" part. A cycle is considered complete after two consecutive empty pages (Telstra's paging returns empty past the end of the real store list rather than erroring), at which point the cursor resets to 0 and `last_full_cycle_at` is stamped.
- New `src/lib/telstra/snapshot.ts`: `snapshotPage(db, input)` reads all stores from D1 (small table, a few hundred rows), computes distance in JS (reuses `shared/scan.ts`'s existing `distance()`), sorts nearest-first, slices the requested page, and joins stock rows for the requested SKUs/stores. Returns `null` if D1 has never been populated, which `src/worker.ts`'s `/api/stock/page` handler treats as "fall back to a live Telstra call" (only relevant in the short window before the first cron cycle after a fresh deploy). `readStatus(db)` powers the new `GET /api/status` route.
- `src/worker.ts`: `validatePage` now rejects any SKU outside `TRACKED_SKUS` (previously just checked the 9-digit format) — this is the "only our SKUs" restriction. New `scheduled()` export wired to `triggers.crons` in `wrangler.jsonc` (`*/15 * * * *`), calling `runIndexCycle` via `ctx.waitUntil`.
- `wrangler.jsonc`: added `d1_databases` binding and `triggers.crons`. **The `database_id` is a placeholder (`REPLACE_WITH_D1_DATABASE_ID`)** — this sandbox has no authenticated Cloudflare session, so the real D1 database has not been created in the user's account. See README "Background indexer" for the exact `wrangler d1 create`/`wrangler d1 execute --remote` commands the user needs to run before deploying; local dev and `deploy:check --dry-run` both work fine with the placeholder (Wrangler doesn't validate the id exists until an actual remote deploy).
- Frontend: `src/client/useStatus.ts` polls `/api/status` every 60s (paused while hidden) — this is the one exception to "no idle polling" and is deliberate/documented in AGENTS.md, since it only ever hits our own cheap status endpoint, never Telstra. `src/components/LastUpdatedBadge.tsx` shows "All N stores updated X ago" in the header, using the *oldest* refreshed store (not the newest) so it can't overstate freshness. `src/components/StoreMap.tsx` (new dependency: `leaflet` + `@types/leaflet`) is a lazy-loaded Leaflet map using OpenStreetMap's free tile server (no API key/billing), rendered above the results list on the Find page — pins are green when a filtered SKU is available at that store, grey otherwise, click opens that store's inventory page. `shared/types.ts` gained `SyncStatus` and an optional `StockPage.snapshotAt`.
- `useScan.ts`/`RadiusGuard`/the client paging loop were **not** changed — the `/api/stock/page` request/response contract is unchanged (`{lat,lon,from,size:10,skus}` → nearest-10-stores page), so the existing incremental-pagination and radius-stop logic keeps working unmodified against the new D1-backed responses.
